# The Loom: see a stranger's USD as data (read-only)

**Date:** 2026-10-07 (rev. 2026-10-08 — scoped to read-only after a design
panel). **What:** the Loom lets you point at a USD stage you didn't build and
**see it as data in seconds** — its profile, its relationships, its table — then
**follow, slice, and certify** what you need. It is deliberately **not an
authoring tool and not a renderer**: it *consumes* what any DCC/pipeline already
authored (native rels, collections, material bindings, schemas) and makes it a
uniform, queryable, surgical, certified data layer.

## Why read-only (the panel finding, recorded so we don't relitigate it)

A three-lens adversarial review (USD-correctness, adoption, strategy) converged:

- **Authoring belongs in the DCC.** The relationships worth authoring are
  spatial/semantic; you must *see the model* to get them right, and the DCC
  already shows it and authors native USD. A data-first authoring app either
  flies blind or rebuilds a worse Solaris.
- **weft already consumes what's authored** — *proven*: a native
  `rel electrical:feeds` authored by any tool is followed (forward and reverse),
  pulled into a surgical closure, and certified (manifest verify clean) with
  **zero weft declaration**; `weft rels` lists what's followable. So the
  authoring "hole" is already filled by USD + the DCCs.
- **The durable value is the read side** — turning uninstrumented, stranger USD
  into queryable/certified data at volume. That's what's built, and what
  survived the panel.

So the Loom's job is everything *up to* authoring: look, understand, slice,
certify. Authoring stays where the geometry is.

## Form: `weft loom <stage>` → a local, data-first web app

A **localhost** server (stdlib `http.server`, no new deps) holds one open stage
+ the pull cache, and opens the browser. Runs on plain `usd-core` — no imaging
build — so any USD opens in seconds on any machine. `--export DIR` writes a
static, self-contained bundle (the profile/graph/table as JSON + the page),
shareable exactly like the artifacts we've published. Localhost-bind only.

## The four panes (all read-only; all over existing weft)

1. **Profile — "what's here".** The data profile computed from the derive
   substrate + `authored_relationship_kinds`: prim count, **% behind payloads**,
   the native relationship kinds present and their counts (what you can
   `--follow`), per-lens relationship counts (hierarchy, material:full/preview,
   collections), materials/collections totals, and **derived-vs-absent** facets.
   The glance that answers "what is this stage, and what's in it" before you
   load a byte — the thing that would have turned our 3-probe material hunt into
   one look.
2. **Graph — the relationships.** The d3 thread viewer
   (`extras/usdview/weftViewer/viewer_template.html`, already standalone),
   driven by the local server: every derived lens, peek/pull/re-center, the
   compose overlay. Read-only exploration.
3. **Table — the stage as data.** `weft data`: prims × columns, the cheap tier
   by default, the `attr:<name>` adder for any attribute/primvar/metadata,
   numeric selection cross-highlighting the graph.
4. **Query bar — find & slice.** A weft-ask/compose expression (including
   `follow:<any native rel>`) → highlights the matching set in graph and table
   with a live cost readout → **Load / export slice** (pull → surgical stage,
   through the cache, instant on repeat) and **certify** (manifest + verify).

## Server API (JSON over localhost; all thin wrappers, nothing new to resolve)

- `GET /profile` → counts + native rel kinds + derived-vs-absent.
- `GET /graph`, `GET /data` → read the stage as relationships / as a table.
- `POST /query` → evaluate an expression to a member set (highlight).
- `POST /pull` → a cached surgical pull; `?out=` writes the layer; returns the
  manifest digest (certify).

Every endpoint reuses `threadgraph.build_graph`, `data.project`,
`pull`/`compose`/`manifest`, and `pull.authored_relationship_kinds` verbatim.
The only new code is the server + the page; there is **no authoring path, no
overlay, no edit target** — which also sidesteps every correctness landmine the
panel found in path-based overlay authoring.

## Files
- **Create** `weft/loom/server.py` + `app.html` (+ small JS/CSS) — the localhost
  server and the four-pane page; the graph pane shares the existing viewer.
- **Modify** `weft/cli.py` — the `loom` verb (`<stage>`, `--port`, `--export DIR`,
  `--no-open`).
- **Create** `tests/test_loom.py` — endpoint contract tests (no browser).

## Testing
- **Server contract (no browser):** on a fixture stage, assert `/profile` counts
  (incl. native rel kinds from `authored_relationship_kinds`), `/graph` shape,
  `/data` columns incl. `attr:`, `/query` membership, `/pull` members + digest;
  localhost-bind asserted.
- **Static export:** `--export` bundle's JSON matches the live endpoints; the
  page loads with no server.
- **Reuse, not fork:** the graph pane is the existing viewer's JS (`node --check`
  stays green).
- **Acceptance on ALab:** `weft loom entry.usda` opens in seconds; the profile
  shows 4,541 prims / 95% payloaded / material:binding:full+preview counts / 114
  collections / native rel kinds; a `follow:material:binding:full` query
  highlights and `Load slice` returns a surgical pull in ~ms on repeat.

## Out of scope (named)
- **Authoring** — any kind; it belongs in the DCC. weft reads what was authored.
- A renderer/viewport; a "see this slice in usdview" hand-off to `weft open` is a
  later convenience, not part of the Loom.
- Multi-stage diff; the learned-similarity (B) lens — later read-only panes over
  the same engine.
